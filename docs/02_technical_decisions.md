# 기술적 결정사항

## 1. API 선택: FilterLogEvents vs Logs Insights

### 선택지 비교

| 항목 | FilterLogEvents | Logs Insights |
|------|-----------------|---------------|
| 비용 모델 | API 호출당 $0.01/1,000건 | 스캔 데이터당 $0.0076/GB |
| 500GB 로그 검색 시 | ~$0.01 | ~$3.8 |
| 쿼리 기능 | 단순 (키워드 필터) | 강력 (SQL-like) |
| 응답 속도 | 빠름 | 느림 (수 초) |
| 여러 로그 그룹 | 불가 | 가능 |

### 결정: FilterLogEvents

**이유:**
- 비용 예측 가능 (호출 기반 vs 스캔량 기반)
- Logs Insights는 로그 많으면 비용 폭탄 가능
- 1단계에서는 단순 조회로 충분

## 2. 비용 분석

### 시나리오: 5명이 실시간 로그 조회 (5초 폴링)

```
API 호출: 5명 × 12회/분 × 60분 × 24시간 = 86,400회/일
월간: 약 260만 회
비용: $0.01/1,000건 = $26/월

데이터 전송: 86,400회 × 100KB = 8.64GB/일
월간: 약 260GB
비용: 무료 100GB 초과분 160GB × $0.09 = $14.4/월

총: 약 $40/월
```

### 캐싱 적용 시

```
백엔드에서 5초마다 1회 호출 → 사용자는 캐시 조회
API 호출: 1/5로 감소
총: 약 $8~10/월
```

## 3. Rate Limit 대응

### AWS 제한

| 항목 | 제한 |
|------|------|
| FilterLogEvents - 계정당 | 5회/초 |
| FilterLogEvents - 로그 그룹당 | 5회/초 |

### 문제 상황

```
5명이 동시에 같은 로그 그룹 조회 → 5회/초 → 한계선
6명 이상 → Throttling
```

### 해결책

| 방법 | 설명 |
|------|------|
| 서버 캐싱 | 백엔드가 주기적 조회, 사용자는 캐시 조회 |
| 폴링 간격 조정 | 5초 → 10초 |
| Service Quotas 상향 | AWS에 요청 (승인 필요) |

### 결정: 서버 캐싱으로 해결

## 4. 크로스 계정 접근

### 현재 계정 구조

```
Root 계정 A ─ 하위 계정들
Root 계정 B ─ 하위 계정들  (각각 완전 분리)
Root 계정 C ─ 하위 계정들
```

### 선택지

| 방법 | 설명 | 적합도 |
|------|------|--------|
| IAM Role Assume | 각 계정에 Role 생성, STS로 임시 credentials 획득 | O |
| Access Key 직접 관리 | 계정별 키 저장 | 보안 위험 |
| AWS Organizations | Root가 분리되어 불가 | X |

### 결정: Role Assume 방식 (2단계에서)

1단계에서는 내 계정 직접 접근으로 시작.

## 5. 데이터 전송 비용 정리

### AWS 무료 티어

- 인터넷으로 나가는 데이터: 월 100GB 무료
- 계정 전체 합산 (CloudWatch만이 아님)

### 오해하기 쉬운 점

```
Q: 로그 그룹에 500GB 있으면 한 번 조회로 무료 끝?
A: 아니다. 전체를 받는 게 아니라 페이지네이션으로 필요한 만큼만 받음.
   - GetLogEvents: 한 번에 최대 1MB
   - FilterLogEvents: 페이징 처리
   - 실제: "최근 5분 로그" = 수 KB~수 MB
```
